# 编码规范 — 通用原则

> 本文件定义所有语言通用的编码约束。
> 语言 / 样式特定约束见同目录对应文件（如 `typescript.md`、`css.md`）；无对应文件时跟随仓库已有代码。

---

## 优先级

语言 / 样式特定规范（如 `typescript.md`、`css.md`）的优先级高于本通用文件，类比 CSS 特异性——更具体的覆盖更通用的。

- 通用原则与语言习惯冲突时，以语言特定文件为准。
- 语言特定文件只写差异与覆盖，不复制本文件正文；通过相对路径引用通用层。
- 可被语言覆盖的通用条目，可在该条目旁标注「语言可覆盖」。

---

## 语言与注释

- 注释语言与项目约定一致；默认**中文**（变量名 / API 名除外）
- commit 说明使用中文
- 专有名词、符号、类型名保持原文

---

## 命名规范

- 遵循当前语言的惯用风格，不要在同一模块混用两套风格
- 名称表达意图，避免无意义缩写
- camelCase / snake_case / PascalCase 等具体风格以语言规范为准；无语言文件时跟随仓库已有代码

---

## 错误处理

- 永远不要静默吞掉错误
- 失败必须被记录或向上传递；具体写法以语言规范为准

---

## 代码质量要求

| 检查项 | 标准 |
|--------|------|
| 函数长度 | ≤ 50 行，超过须拆分 |
| 文件长度 | 200–400 行典型，最大 800 行 |
| 嵌套深度 | ≤ 4 层，超过用提前返回或抽函数 |
| 魔法数字 | 抽取为命名常量 |

### 简洁优先

- 优先写直接、可读、可验证的实现；不要为了显得"架构化"制造层级。
- 只有满足下列条件之一才新增抽象：真实复用、隔离复杂度、稳定职责边界、隐藏外部依赖细节。
- 不为"未来可能会用"提前抽象；未来需求出现时再提取。
- 删除无用代码优先于注释解释无用代码；保留兼容路径必须写明触发条件。
- 让调用点读起来像业务意图，而不是暴露一串实现步骤。

---

## 通用禁止事项

- ❌ 禁止硬编码敏感信息（密钥、token、密码）
- ❌ 禁止代码中出现 mock 数据作为兜底逻辑
- ❌ 禁止修改 Lint / 格式化 / 提交钩子配置（除非明确要求）
- ❌ 禁止未经验证就声明完成

语言专属禁止项（`any` / `var` / `==` / `console.log` 等）见 `typescript.md`；样式专属禁止项见 `css.md`。不要把这些当作全项目铁律。

---

## 文件组织原则

- 多个小文件 > 少量大文件
- 高内聚，低耦合
- 按功能 / 领域组织，而非按文件类型
- 200-400 行典型，800 行最大
- 新文件必须有清晰职责；如果只是把 10 行代码搬到新文件且没有复用或隔离价值，不要拆
