# 上下文模式：Loop 自动化模式（Loop Automation）

> 触发时机：需要定时心跳检查、自动巡逻、周期性质量门禁。
> 作用：用 `/loop` 代替人工重复触发，让 Agent 按固定节奏自动检查并报告。

---

## 核心思想

人工手动触发每次检查不应是常态。以下重复性工作应交给 Loop：

- 周期性质量巡检
- 长时间任务的进度追踪
- 跨会话的进度跟踪（需要 durable）
- CI/CD 失败后的自动修复尝试

---

## 自动化场景分级

| 级别 | 场景 | 频率 | 示例 |
|------|------|------|------|
| **心跳** | 确保 Agent 不僵尸 | 每 10-20 分钟 | `/loop 15m` 检查长任务是否卡住 |
| **巡逻** | 周期性质量巡检 | 每 30-60 分钟 | 检查 lint/type-check 是否通过 |
| **看门狗** | 外部事件响应 | 每 1-5 分钟 | 监控 CI 状态、PR review 状态 |
| **定时任务** | 按计划触发 | 每天/每周 | 依赖审计、记忆清理、过期分支检查 |

---

## 使用 `/loop` 的时机

### 适用

- 同一种检查需要在多个时间点重复执行
- 等待外部异步结果（CI、Code Review、Agent 回复）
- 跨会话的进度跟踪（需要 durable）
- 已确认检查逻辑可靠，不需要每次人工确认

### 不适用

- 一次性任务
- 需要每次人工判断的新场景
- 检查逻辑本身还在调试中
- 用户明确说"不用自动化"

---

## Loop 安全约束

```text
无预算 = 不启动 | 无进展 = 自动退出 | 异常 3 次 = 升级人工
```

### 硬性限制

| 约束 | 值 | 说明 |
|------|-----|------|
| 最大重试 | 3 次 | 连续失败 3 次自动退出并通知用户 |
| Token 预算 | ≤ 50k/次 | 单次巡检消耗上限 |
| 无进展退出 | 连续 3 轮 | 3 轮检查输出与上轮完全一致（无新文件、新错误、新状态变化）自动退出 |
| 会话级 Loop | 默认 | 仅 `/loop` 不传 `durable` |
| 持久化 Loop | 用户明确要求 | 仅 Claude Code：写入 `.claude/scheduled_tasks.json`（没有该文件时创建，不要先去读一份仓库里不存在的配置）。其他工具用其自身定时能力，不要假装已接线 |

### 启动前检查清单

- [ ] 检查逻辑是否已验证无误（至少手动跑过一次）
- [ ] 是否有明确退出条件（不是死循环）
- [ ] Token 预算是否合理
- [ ] 用户是否已知晓并同意

## 通用适配原则

不假设一定使用某个语言、框架或包管理器。启动 Loop 前必须先确认真实验证命令：

- 优先读取项目入口说明：`AGENTS.md`、`README.md`、`AI_MEMORY.md`
- 再检查工具配置：`package.json`、`Makefile`、`justfile`、`scripts/`、CI 配置
- 只运行已确认存在的命令；未确认时先手动跑一次，不直接写入 Loop
- 示例中的 `pnpm` / `gh` / `bash scripts/*` 仅是候选命令，不是默认假设

## 每轮报告格式

```text
【Loop Round N】
触发原因：[心跳 / 巡逻 / 看门狗 / 定时任务]
执行命令：[命令或检查动作]
状态变化：[新错误 / 新文件 / 新状态 / 无变化]
验证结果：[通过 / 失败 / 无法验证]
退出判断：[继续 / 无进展退出 / 异常升级 / 已完成]
下一步：[下一轮动作 / 交人工决策]
```

## 推荐自动化配置

### 1. 质量巡逻（开发阶段）

```bash
# 每 30 分钟运行项目已确认的最小质量门禁
/loop 30m "运行本项目已确认的最小验证命令（如 lint/type-check/test/validate-spec），如有失败列出命令、文件和错误；无失败则报告通过；不要自动修改代码"
```

常见候选命令（仅在项目中确认存在后使用）：

- JS / TS：`pnpm lint && pnpm type-check && pnpm test`
- Make 项目：`make test` 或 `make check`

### 2. CI 看门狗（等待 PR）

```bash
# 每 3 分钟检查 CI 状态
/loop 3m "用项目已配置的 CI 查询方式检查当前 PR 状态，通过则通知我，失败则列出失败项和日志入口；不要直接修复"
```

### 3. 依赖审计（定期）

```bash
# 每天检查一次依赖安全（仅在项目已配置依赖审计命令时）
/loop 1440m "运行项目已确认的依赖审计命令，如有严重漏洞列出影响范围和建议修复方案；不自动升级依赖" --durable
```

### 4. 模式回顾

不要用 `/loop` 定时刷 `AI_MEMORY.md` 观察项。有实质性改动的收尾才按 `continuous-learning.md` 计数；达阈值当面问用户。

## Loop 与审查闭环的配合

审查-修复闭环（`collaboration.md`）是带 task ledger 的有界 Loop；审查轮次和停止规则唯一来源为 `quality-checklist.md`：

```text
完整审查 → 按 ledger 路由修复 → 携带同一 ledger 复审
                                  ↓
                      按 quality-checklist 继续或升级
```

停止或升级前，必须完成当前 review pass 并保存完整 ledger；存在未解决 CRITICAL/HIGH 时不得合入。这个 Loop 内置在协作流程中，不需要单独 `/loop` 命令。

---

## 禁止行为

- ❌ 未经验证检查逻辑就启动 Loop
- ❌ 无退出条件的死循环
- ❌ 无 Token 预算上限的长期 Loop
- ❌ 持久化 Loop 未经用户明确同意
- ❌ Loop 内执行破坏性操作（reset、force push、删除文件）
- ❌ 未确认项目命令就套用示例命令
- ❌ Loop 内直接做结构性修复；结构变更必须回到任务路由和模式判断
