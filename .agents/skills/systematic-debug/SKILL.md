# 系统化调试（Systematic Debugging）

> 未完成根因调查，不得进行任何修复。本地执行见 `workflow.md`，回归测试见 `testing-guidelines.md`。

## 使用边界

使用：测试失败、生产 bug、异常行为、性能、构建/集成失败；尤其想「快速试一下」或已试多次仍未解决。

不使用：类型错误、lint、原因一目了然的单行逻辑错误；用户已给出明确修复且原因已确认。

---

## 四阶段（不得跳过）

| 阶段 | 做完才进入下一阶段 |
|------|-------------------|
| **1 根因** | 读完整错误与堆栈；稳定复现；看 `git diff` / 依赖 / 环境；沿数据流向上追溯到源头，不在症状处修 |
| **2 模式** | 找仓库里能工作的类似代码，列出每一个差异，不要假设「那个不可能有关系」 |
| **3 假设** | 一次一个假设，最小改动验证。有效 → 阶段 4；无效 → 新假设。不知道就说不知道 |
| **4 修复** | 有测试栈：先写失败回归测试（`test-driven-development`）再修。无测试栈：不引入测试工具，用仓库已有命令或手动复现验证，并注明跳过回归测试。只修已确认根因。失败少于 3 次回阶段 1；**达到 3 次停下来质疑架构**，先跟用户讨论 |

根因修复后再问：同样错误在入口 / 中间层 / 执行处能否再拦住。

## 常见借口与反驳

| 借口 | 现实 |
|------|------|
| "问题很简单，不需要流程" | 简单问题也有根因。流程对简单 bug 也快。 |
| "紧急情况，没时间走流程" | 系统调试比猜测试错快得多。 |
| "先试这个，再调查" | 第一次修复就定了基调。从一开始就做对。 |
| "我看出问题了，直接修" | 看出症状 ≠ 理解根因。 |
| "再试一次修复"（已 2 次以上） | 3 次以上就是架构问题。质疑模式，不再修复。 |
| "我手动验证就行，不用测试" | 有测试栈时必须先写失败回归测试。无测试栈才允许用已有命令或手动复现，并注明跳过。 |

## 红牌 — 停，回到阶段 1

- "先快速修一下，之后再调查"
- "试试改 X 看有没有用"
- "同时改几处，跑测试"
- 有测试栈却说"跳过测试，我手动验证"
- "应该是 X，直接修"
- 提出修复但没有回溯数据流
- 已经试了 2 次以上还要「再试一次」
- 每次修复都在不同位置揭示新问题
