# Test-Driven Development (TDD)

> 如果没看着测试失败，就不知道它测试的是不是正确的东西。
> Mock 原则与 TDD 反模式见 `testing-guidelines.md`，本文件不重复。

---

## 执行卡片

必须：

- 先读 `AGENTS.md`、`.agents/testing-guidelines.md`、`.agents/coding-standards/common.md`
- 先确认仓库是否有测试运行器；没有则跳过本 skill，用已有命令或手动步骤验证并注明
- 有测试栈时：先写或定位失败测试；看见正确失败后再写最小实现
- GREEN 后做行为验证和边界实测
- 交付时报告 RED / GREEN / REFACTOR / 验证证据，或写明跳过 TDD 的原因

禁止：

- 有测试栈时，没有失败测试就写生产代码
- 删除或回退用户已有改动
- 用未运行的测试结果声称通过
- 交付 `.only` / `.skip`、临时断言或只在 console 里验证过的状态

---

## 铁律

```text
有测试栈：没有失败测试之前，不写任何生产代码
无测试栈：不引入新测试栈；验证用仓库已有命令或手动步骤，交付中注明跳过
```

测试前写了本轮自己可安全丢弃的实现：删除或隔离，从测试重来。不删除、不回退用户已有或来历不明的改动；分不清时先隔离或询问。

## 使用边界

有测试栈时使用：新功能、bug 修复、重构、行为变更。

不使用（与 `testing-guidelines.md` 一致）：仓库没有测试运行器或覆盖率工具。不引入新测试栈。

需用户同意才能例外：一次性原型、自动生成代码、纯配置文件。

---

## 流程

1. **RED**：写一个最小测试展示目标行为。运行器、后缀跟随仓库已有约定。一个用例一个行为；优先测真实代码。
2. **验证 RED**：失败必须来自预期断言或明确未实现，不是语法/导入/环境错误。立即通过 → 测试写错了。
3. **GREEN**：最小实现让测试通过。不超出测试覆盖，不顺手重构，不为测试暴露生产 API。
4. **验证 GREEN**：新测试通过，相关旧测试仍通过。
5. **行为验证**：过 `testing-guidelines.md` 的 TDD 反模式。边界实测覆盖空值、非法/超限、时序/并发中与本改动相关的项。console 不能替代测试。
6. **REFACTOR**：仅在 GREEN 和行为验证后；复跑相关测试。

---

## 红牌

出现以下情况必须停下：测试前写了生产代码；实现后补测试；测试立即通过却算覆盖；解释不了 RED 为何失败；「稍后再补」「这次很简单」「已经手动测过」「留着实现当参考」「删掉太浪费」。

处理：本轮可丢弃实现 → 删除或隔离后用 TDD 重来；涉及用户已有改动 → 先询问。

---

## 交付模板

```text
【TDD 证据】
RED：[命令 + 正确失败原因]
GREEN：[命令 + 通过结果]
REFACTOR：[是否执行；执行后验证命令]

【行为验证】
真实行为 / 测试污染 / mock 边界：[结果或 N/A]
边界实测：[输入 -> 结果]
临时测试清理：[无 .only/.skip]
```

无测试栈跳过时，【TDD 证据】写「跳过」及原因，验证证据改填仓库已有命令或手动步骤。禁止输出"功能正常""逻辑没问题""看着可以"这类不可复现结论。有测试栈时任一项没完成，不算完成 TDD。
