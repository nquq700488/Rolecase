# 任务记忆规范

> `TASK_MEMORY.md` 只回答一件事：**下次打开仓库，怎样接着干？**
> 可复用结论写 `AI_MEMORY.md`。操作流水不写进本文件。

---

## 什么值得记

主规则只有一条：

- **不记的话，下回继续任务要重新分析上下文，就写。**

文件里只该出现两种状态：**`[进行中]`**（开发中 / 待开工）、**`[已搁置]`**（用户明确说暂不处理）。

`[已完成]` 只是**过渡标记**：开发结束的判据是**代码写完没有**，不是验证通过没有——别等验证。先把可复用结论升到 `AI_MEMORY.md`，随即**删掉条目**——干过什么由 `git log` 和 `AI_MEMORY.md` 回答，任务记忆里堆积 `[已完成]` 就是噪音。

标题就是 `[状态 日期]`，**不带任何后缀**。这些一律不写：① 验证与上线观察（「用户实测通过」「reviewer PASS」「未真机验证」「待上线观察」）——那是过程，观察类信号归 `AI_MEMORY.md` 的「观察中模式」；② git 状态（已提交 / 未提交 / hash）；③ 状态词的同义反复（`[已搁置]` 不写「用户决定暂不处理」）。真正还没闭环、下回要动手的事写进正文的「阻塞或未决」。

**不记 git 状态**（提交 / 未提交 / 分支 / commit hash）：`git status`、`git log` 就是权威，抄进任务记忆只会过期。任务记忆记的是「下回怎么接着干」，不是「仓库现在长什么样」。

机械小改、单文件微调、纯配置加减、文案改动不写。

主动压缩前：有未完成则更新四行。压缩摘要、交接全文不写进本文件。

不写：

- 操作步骤、代码片段、before/after
- 已验证的「以后都按这个做」（升 `AI_MEMORY.md`）
- Reviewer 清单、批次流水、压缩草稿里的过程信息

---

## 记录格式

新条目插在第一个 `---` 之后，时间倒序。

```markdown
## 任务标题 [进行中]
目标：一句话
状态：进行到哪 / 下回从哪继续
阻塞或未决：无 / 一句（未拍板的取舍只在这里保留「排除」）
涉及文件：路径列表
```

四行够用。不要强制「方案 + 排除 + 踩坑关键词」那套长模板。

---

## 开发结束时

1. 命中 `AI_MEMORY.md` 写入条件 → **只把结论写过去**
2. **从本文件删掉该条目**——不是压成摘要，是删除
3. 只有「还没闭环、且下回确实要接着干」的事才另起一条（如待联调、待排期），其余一律不留
4. 同一条决策禁止在两个文件各写一遍

长流程或并行时，子任务状态以本文件为准，禁止凭对话记忆重派已完成工作。
