# 测试规范

> 测试编写、验证约束、验收标准格式的唯一来源。
> TDD 循环见 `skills/test-driven-development/SKILL.md`。Reviewer 门禁见 `quality-checklist.md`。方案与影响面见 `planner.md`。

仓库**没有**测试运行器或覆盖率工具时：不引入新测试栈，验证用仓库已有命令或手动步骤，并在报告里写明跳过原因。

---

## 写测试（有测试栈时）

- **测什么**：被多处依赖的公共模块、核心业务逻辑必须测。不要为仓库里不存在的层补测试（无 UI 不写组件测试，无 HTTP 不写接口测试）。
- **覆盖率**：仅当仓库**已经**配置覆盖率门禁时遵守该门禁。不要发明「全仓库 80%」或为凑数字测实现细节。
- **放置**：跟随仓库已有约定；没有约定时与被测文件同目录或同语言惯用目录。
- **描述**：用例说明用中文。测试函数 / 方法名跟随当前语言惯例，不要把 `应该{结果}` 套到 `test_*` / `Test*` 标识符上。
- **运行器、后缀、断言 API**：以仓库已有代码为准，不要为迁就示例引入依赖。

禁止：一个用例测多个行为；测内部变量等实现细节；单元测试打真实网络；过度 mock 导致测的是假对象。

### Mock

- 用工厂或等价方式造数据，每次新对象，不共享可变状态
- mock 外部依赖（网络、文件系统、浏览器 API 等），不 mock 本测试要验证的逻辑
- 集成测试优先 mock 最外层外部依赖
- 同一条链路不要混用两套 mock 策略
- mock 的数据形状要够下游不崩；不要为未走到的字段堆完整宇宙，也不要只填当前断言用到的一两个键就宣称「完整」

### TDD 反模式（原则）

1. 测真实行为，不要断言「mock 被调用了」或「mock 组件存在」
2. 不要给生产类型加仅测试用的方法；放到测试工具
3. 不理解副作用就不要 mock；不确定时先跑真实实现
4. 测试是实现的一部分，不要事后补。例外与 `test-driven-development` 一致：一次性原型、生成代码、纯配置，或仓库无测试工具——须用户同意或在交付中注明跳过

## 验收标准（Planner 产出，Tester 核查）

影响面来自方案里的调用方 / 模块 / 接口 / 数据流（见 `planner.md`），不是单独文件。

```markdown
#### 子任务 N：[名称]

| 场景分类 | 场景 | 前置条件 | 操作步骤 | 预期结果（可量化） | 不应发生 | 验证方式 |
|---------|------|---------|---------|-----------------|---------|---------|
```

- `场景分类` 只能：`正向 / 异常 / 边界 / 回归`
- `验证方式` 只能：`自动 / 手动 / N/A（原因）`
- 不适用必须 `N/A（原因）`，不得省略

### 最小覆盖

- 每个子任务至少 1 条 `正向`，无豁免
- 命中接口调用、异步切换、状态写入、路由切换任一项时，再补 1 条 `异常` 或 `边界`
- 方案影响面里有消费方时，补 1 条 `回归`
- 纯样式 / 纯文案 / 纯静态展示可豁免异常、边界、回归，但须 `N/A（原因）`
- 多个独立行为不能只写 1 条总验收

`正向` 必填。`异常` / `边界` 只写**本任务真实存在**的失败模式（超时、空值、无权限、并发等）；前端三态、DOM、token 仅 UI / Web 任务适用。`回归`：全新功能且无调用方可豁免。

### 潜在问题清单

Planner 填 `存在 / 不存在 / N/A（原因）`，不得留空。`存在` 必须在验收表有对应项。Tester 发现清单为 `存在` 但表未覆盖 → 打回 Planner。

```text
□ 重复请求：并发或重复触发导致多次副作用？
□ 竞态：异步顺序不确定导致覆盖？
□ 资源泄漏：监听 / 定时器 / 句柄未释放？
□ 状态残留：流程结束后共享状态是否应重置？
□ 数据丢失：中途退出是否丢未提交数据？
□ 外部依赖：未就绪或失败是否有处理？
□ 等待 / 失败 / 空：是否有明确反馈（无 UI 则 N/A）
□ 不可逆操作：是否有确认或等价保护？
□ 副作用扩散：是否意外打到其他模块？
```

## 怎么验

- 优先用仓库已有的单元 / 集成 / 浏览器测试。没有浏览器测试工具时，不要为迁就本规范安装 Playwright
- 已使用 Playwright：优先本机 Chrome（`channel: 'chrome'`），禁止无参 `chromium.launch()` 去下自带 Chromium
- 稳定逻辑、接口、状态、边界 → 优先自动；视觉、真机、外部联调、体感 → 可手动，须写出步骤和观察点
- 同一条验收不得只写「人工验证」或「测试通过」

---

## Tester 验证质量门禁

看起来能跑 ≠ 通过。必须按验收表、影响面、改动文件、实际命令和结果判断。

- **验收完整性**：正向 / 异常 / 边界 / 回归是否按最小覆盖；缺项是否有 `N/A（原因）`
- **影响面覆盖**：方案里列出的消费方、接口、状态、入口是否有对应验证
- **执行真实性**：写出命令、手动步骤、环境、结果；禁止只写「已验证」
- **证据**：断言、日志、截图、响应或数据变化能支撑结论
- **回归**：周边旧能力；高风险未测不得放行
- **可复现**：失败须含前置、步骤、期望、实际、稳定性
- **未测风险**：显式列出

| 严重级别 | 判定标准 | 处理 |
|----------|----------|------|
| CRITICAL | 核心验收失败、关键测试命令失败、数据安全/主流程不可用 | 阻断 |
| HIGH | 表面可用但关键异常、边界、回归或影响面未验证；无可复现证据 | 阻断 |
| MEDIUM | 局部覆盖不足或证据不完整，不影响当前合入判断 | 记录并建议 |
| LOW | 描述、截图命名、报告格式 | 建议 |

主路径通过但关键风险未测 → 至少 HIGH 或 MEDIUM，不得以「功能可用」通过。HIGH 须回 Developer 或 Planner 补齐后复测。

```md
## Tester 结论

可通过：是 / 否
总体评价：[覆盖和证据质量，不只功能是否可用]

### 覆盖矩阵
| 验收项 | 场景分类 | 验证方式 | 执行结果 | 证据 | 结论 |
|--------|----------|----------|----------|------|------|

### 阻断问题
- [CRITICAL/HIGH] 场景 — 问题、证据、复现步骤、建议修复方向

### 非阻断建议
- [MEDIUM/LOW] 场景 — 问题、影响、建议

### 未验证 / 无法验证
- [场景] — 原因、风险、建议后续验证方式

### 已执行命令 / 手动步骤
- [命令或步骤] — 结果

### 剩余风险
- [没有则写「无」]
```

## 禁止的模糊描述

| ❌ | ✅ |
|----|----|
| 显示正确 | 列表第 1 位标题为「测试」 |
| 样式正常 | 写出可核对的样式约定（token 或计算值，不要发明色值） |
| 功能可用 | 点击保存后 3 秒内弹窗关闭 |
| 请求发出了 | 指定接口只发起 1 次 |
| 状态更新了 | 写出字段从何值变为何值 |
| 异常有处理 | 失败时展示「加载失败，点击重试」或等价可观察结果 |
