# 技术选型说明

> 本文承接 [调研与决策.md](../../调研与决策.md) 的「二、最终技术决策」，记录各项选型的理由与约束。
> 决策表本身在主文档，本文只写「为什么这么选」和「边界在哪」。

## 1. HTTP 层：Fastify 而不是 NestJS

评估过 NestJS，最终不采用：

- **DI 的价值有限**。项目定义的 Port 数量有限（`AgentRuntimePort`、`CapabilityDiscoveryPort`、`RepositoryPort`、`CredentialStorePort`、`EventBusPort`、`EventStorePort`、`ClockPort`、`IdGeneratorPort`），手写装配约 30 行即可，不值得引入装饰器框架；
- **会出现第二套模块系统**。项目已用 `docs/modules/*.md` 定义模块边界，NestJS 的 `@Module({ providers, controllers })` 会成为第二个真相来源，违反 `.agents/spec-governance.md` 的唯一来源原则；
- **架构红线从「靠规则守住」变成「结构上写不出来」**。用 Fastify 时 `domain` / `application` / `contract` 里没有任何框架可 import；用 NestJS 则必须靠机检规则去拦装饰器泄漏，且仓库里会同时存在两套写法；
- **与项目编码规范一致**。`.agents/coding-standards/common.md` 要求「不要为了显得架构化制造层级」「不为未来可能会用提前抽象」；
- **桌面打包更简单**。Fastify 是普通 Node 依赖；NestJS 需额外携带 `reflect-metadata` 与装饰器元数据。

手写装配同样是依赖注入，只是不用装饰器，构造函数注入的测试友好性完全保留。

后续若 HTTP 面显著变大，可以只增加一个轻量容器（`awilix` 或 `tsyringe`），它仍然只是容器，不会变成第二套模块系统，也不需要重写业务代码。

**改选 NestJS 的条件**：团队对 NestJS 的熟悉度带来明显速度优势；或后端预期长成大规模 HTTP API。此时 NestJS 仍只允许出现在 `http-ws` 与装配层。

- Web UI 只依赖 Contract、HTTP/WS Client 和 PlatformHost，不直接依赖 Tauri / Electron。

## 3. 网络层统一封装

前后端都必须经过封装层，不允许业务代码直接调用网络 API。

**HTTP 客户端选 axios，不用裸 fetch**：

- 拦截器是这个项目的真实需求：注入 Local Token、解包 `{ok, error}` 信封、错误码归一化、脱敏日志、透传 request_id；
- 超时与取消开箱可用，不用自己用 `AbortController` 拼；
- `fetch` 对 4xx / 5xx 不 reject，每个调用点都要判 `res.ok`，容易漏；axios 统一 reject，错误归一化只需一处；
- Vue 生态里 axios + 拦截器是主流做法，自定义代码维护面更小；
- 体积代价（约 13KB gzip）对本地应用无影响。

**改选 fetch 的条件**：需要浏览器原生流式响应（SSE），或需要极致体积控制。本项目事件流用 WebSocket，两者都不适用。

**前端**：`apps/web/src/api/` 下集中封装 HTTP 客户端与 WebSocket 客户端，见 [Web UI 模块](../modules/web.md)。

**后端**：统一错误信封、request_id 回传、结构化脱敏日志、超时、请求体上限与优雅关闭，见 [HTTP/WS 模块](../modules/http-ws.md)。

**共同约束**：错误信封、request_id 回传、重试退避与事件续传属于 wire 行为，唯一定义在 [数据模型与 API](数据模型与API.md)。

## 4. 接入层实际路径与能力边界

### 4.1 实际链路

```text
Rolecast
  │  ACP（JSON-RPC over stdio）
  ▼
ACP Adapter（子进程）
  ├── claude-agent-acp ──→ @anthropic-ai/claude-agent-sdk ──→ Anthropic API
  └── codex-acp ─────────→ cross-spawn 启动捆绑的 @openai/codex ──→ OpenAI / 兼容 API
```

两个 Provider 的底层形态**不一样**：

| Provider | Adapter | 底层是 | 说明 |
| --- | --- | --- | --- |
| Claude | `@agentclientprotocol/claude-agent-acp` | Claude Agent SDK（库） | SDK 内嵌 Bun 编译的 Claude Code 运行时，运行时解包启动 |
| Codex | `@agentclientprotocol/codex-acp` | Codex CLI（捆绑） | 通过 `cross-spawn` 拉起 `@openai/codex` |

**易误解点**：Claude 这条路径不会用到用户本机安装的 `claude` CLI（`@anthropic-ai/claude-code`）。链路里确实有 CLI 形态的进程，但它是 SDK 自带的那一个。

**API Key 只改变凭据供给方式**（OAuth vs 环境变量 / base URL），不改变链路形态，也不会绕过 Adapter。

### 4.2 谁提供工具能力

**Rolecast 不实现工具能力，也不实现 Agent 循环。** 工具集、权限系统、上下文压缩、子 Agent、MCP 客户端都由 SDK / CLI 提供。

| Rolecast 负责 | Rolecast 不负责 |
| --- | --- |
| 启动 / 管理 Adapter 子进程 | 实现文件读写、命令执行等工具 |
| 讲 ACP 协议 | 实现上下文压缩 |
| 供给凭据（env / base URL / config） | 实现权限系统本身 |
| **权限请求中转**（转发给 UI 再回传） | 实现 MCP 客户端 |
| 权限模式、工作目录、配置的翻译 | 实现子 Agent 调度 |
| 事件呈现与持久化 | 猜测 Provider 有哪些工具 |
| 能力发现（ACP 握手） | — |

「权限请求中转」转发的是 **Claude Code 自己的权限系统**产生的请求，不是 Rolecast 自建的权限模型。

### 4.3 能力边界约束

- **不得按 CLI 行为推断 Adapter 能力。** SDK 模式会拒绝部分 CLI 命令（例如 `/mcp reconnect`、`/mcp enable`、`/mcp disable` 被拒，Adapter 只能绕道 SDK control API）。CLI 能做的事，通过 ACP 不一定能做。
- **两个 Provider 能力集不对等。** 工具集名称与语义不同；权限模型不同（Claude 是 allow/deny 规则 + 权限请求，Codex 是沙箱模式 + 审批）；上下文压缩与 MCP 支持方式也不同。
- 因此 Provider 差异**只允许出现在 `acp-runtime`**，Orchestration 不得按 Provider 分支。
- **文件访问范围由 Adapter 控制，不是 Rolecast 拦截。** 工具执行在 SDK / CLI 内部，Rolecast 无法事后拦截读写；它只能正确传工作目录与权限模式，并保证不传错路径。

### 4.4 版本记录

Adapter 必须使用 lockfile 精确版本，并把版本写入能力缓存。**当前开发基线锁定：**

```text
@agentclientprotocol/claude-agent-acp@0.90.0
@agentclientprotocol/codex-acp@2.2.2
```

版本必须同时写入 package manifest 和 pnpm lockfile；ACP Spike 与 Contract Test 使用 lockfile 安装，不允许运行时自动升级。SDK 与 CLI 版本编号体系不同（SDK `0.3.x` / CLI `2.1.x`），内嵌运行时版本可能与最新 CLI 存在偏差，不得假设同步。升级必须先重跑握手、配置、权限、取消、恢复和隔离测试。

### 4.5 实测结果

上述能力已经实测验证，含握手能力对比、会话配置项、权限请求报文形态与发现的坑，见 [接入层能力矩阵](接入层能力矩阵.md)。该文档是接入层事实的唯一来源，Adapter 升级后必须重测。

### 4.6 认证处理决策

两个 Provider 的认证路径**不对称**，Rolecast 按各自实际情况处理：

| Provider | ACP 暴露的认证方式 | Rolecast 的处理 |
| --- | --- | --- |
| Codex | `api-key`、`chat-gpt` | 可在配置页驱动认证 |
| Claude | **无**（`authMethods: []`） | 只读取运行环境已有的凭据，不做 UI 内登录流程 |

Claude 侧的具体做法：

- 依赖运行环境已有的 `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_API_KEY` / `ANTHROPIC_BASE_URL` 或本机已登录状态；
- 配置页只显示「已配置 / 未配置 / 需要重新验证」三种脱敏状态；
- 未配置时给出明确指引（在环境变量中配置，或先在本机 CLI 完成登录），**不提供登录表单**；
- 不得因为 `authMethods` 为空就判定 Provider 不可用——实测中 Claude 报「Not logged in」但执行完全正常。

### 4.7 运行环境策略与配置权威

**默认继承用户环境，但每个 ProviderConnection 都显式记录 `environment_mode`：**

```text
environment_mode = inherited | isolated
```

默认值为 `inherited`，用于保持已有登录态和本地配置的开箱可用性；`isolated` 是按 Provider 分别实现的高级选项。无论采用哪种模式，**ProviderConnection 都是 Rolecast 配置的唯一权威**：运行时不得让全局文件静默覆盖 Workspace 中已经保存的连接配置。

**隔离能力已实测**（见 [接入层能力矩阵](接入层能力矩阵.md) §8）：

| Provider | 隔离入口 | 隔离效果 | 第一版策略 |
| --- | --- | --- | --- |
| Claude | `CLAUDE_CONFIG_DIR` | 用户个人命令 66 → 47，全局目录未被写入；环境凭据和模型仍可用 | 可直接启用；隔离目录只承载运行时状态，不复制全局技能 |
| Codex | `CODEX_HOME` | 用户命令 60 → 0，全局目录未被写入；网关、模型目录和登录态消失 | 默认继承；启用隔离前必须完成配置导入或首次引导 |

Codex 隔离采用以下流程：

1. 从用户选择的 `~/.codex/config.toml` 读取**非秘密配置**，只生成待确认的导入草稿；
2. 用户确认后，将 base URL、网关类型、模型目录和推理默认值写入 ProviderConnection；不把整份 TOML 或 OAuth 文件复制到隔离目录；
3. ACP Runtime 把 ProviderConnection 翻译成当前 Adapter 版本支持的显式配置入口，具体字段以能力探测和 Adapter Contract Test 为准，不假设某个未验证的环境变量；
4. API Key 通过 `CredentialStorePort` 的 `credential_ref` 注入；登录流程不在产品范围，隔离环境不接受继承的登录态，也不能静默复制；
5. 导入未完成或字段不完整时显示「需要配置」，**不得静默回退到 inherited**。

配置导入必须区分 preview 和 apply：preview 只读文件并返回脱敏草稿，apply 经过用户明确确认后才写入 Rolecast 配置。导入过程不修改 `~/.codex`，也不保存原始凭据。

这套策略使「隔离运行时状态」与「Rolecast 管理的连接配置」分离，避免软链接全局配置导致配置来源再次失去唯一性。

### 4.8 权限请求超时策略

权限请求不能依赖 HTTP 请求一直保持连接，也不能因为用户暂时离开就自动批准。Rolecast 采用两级超时：

| 阶段 | 默认值 | 行为 |
| --- | --- | --- |
| 软超时 | 5 分钟 | 发送 `agent.permission_overdue`，UI 提升提醒；请求仍保持 `pending`，不自动裁决 |
| 硬超时 | 30 分钟 | 标记 `expired`，向 Adapter 回传拒绝/取消，Run 标记 `interrupted`，不自动重跑 |

权限请求创建时，Run 进入 `waiting_user`，所属 Task 进入 `paused`；因此前端可以离开页面后通过事件和快照恢复现场。硬超时后的回答必须返回状态冲突，不能再转发给 Adapter。`interrupted` 不是业务失败终态，用户可以查看原因后继续或创建新的重试 attempt。

软、硬超时都由服务端持久化的 `expires_at` 驱动，服务重启后根据数据库重新安排，不依赖浏览器定时器。硬超时默认 30 分钟，但可在 Workspace 策略中关闭或调整；关闭硬超时仍保留软提醒和显式用户处理要求。

### 4.9 与 AionCore 的路线差异

AionUI 的 Rust 后端 AionCore 在同一对 Provider 上**不走 ACP**：它把 claude/codex 路由到自实现的 direct-CLI 通道（`--print stream-json` / app-server JSON-RPC），把 ACP 留给其余 18+ 个 vendor。提交 `14efff8`（PR #609）称 ACP Adapter 为「third-party ACP shim」。

Rolecast 仍以 ACP 为默认路径（ADR-003 / ADR-027），理由是实测已证明 ACP 覆盖本项目所需能力，而直连原生协议需要自实现两套 CLI 协议。完整的证据、迁移动机与逃生口说明见 [接入层能力矩阵](接入层能力矩阵.md) §7。

## 5. 工程基线决策

### 5.1 Node 版本

采用 **Node 22 LTS**。实测环境 v22.21.1 可正常运行两个 Adapter；Adapter 自身要求 `>=18`。Node 22 同时内置 `node:sqlite`，作为 `better-sqlite3` 的退路。

### 5.2 SQLite 驱动

采用 **`better-sqlite3`**：

- 同步 API，事务代码简单直接，不必在本地数据库上引入 async 开销；
- 成熟稳定，prebuilt 覆盖主流平台；
- 与 Electron / Tauri sidecar 场景验证充分。

**不选 `node:sqlite`**：Node 22 中仍标记为实验性，API 可能变动。
**不选 `libsql`**：功能超出本地单进程需要，徒增体积。

代价：原生模块，跨 Node / Electron 版本需要重编译。本地应用可接受。

### 5.3 端口策略

**动态分配 + 启动探活**，不使用固定端口：

1. 优先尝试约定端口，被占用则退回系统分配；
2. 实际端口通过 sidecar stdout 或端口文件暴露给桌面壳；
3. 前端不硬编码端口，由启动流程注入。

理由：固定端口在用户机器上可能被其他程序占用，导致应用直接起不来。

### 5.4 Local Token 传递和存储

默认采用短生命周期 Token，不把原文写入 SQLite：

1. 服务启动时生成 256 bit 随机 Token，并只保存在 Server 进程内存；
2. 经 **URL fragment** 交付：`http://127.0.0.1:<port>/#token=<token>`（fragment 不会进入服务端日志与 Referer）；
3. 前端读取后**立即清除 hash**；
4. 前端存储在 **`sessionStorage`**，不写 `localStorage`；
5. Server 重启时生成新 Token，旧浏览器 Token 失效，启动流程重新交付 Token。

`sessionStorage` 的理由：同源策略下其他来源读不到，刷新页面不丢失，关闭标签页即清除。服务端内存只保存当前有效 Token，避免数据库备份、诊断包和迁移流程带出可直接使用的控制面凭据。

如果未来需要跨 Server 重启保留 Token：原文只能进入系统 Keychain；SQLite 只保存 `token_hash`、`issued_at`、`expires_at`、`revoked_at` 等生命周期元数据。SQLite 禁止保存 Local Token 原文；高熵随机 Token 的 Hash 可使用 SHA-256，并在比较时采用常量时间比较。该模式必须明确轮换和撤销策略。

### 5.5 其他基线

| 项 | 决策 |
| --- | --- |
| 迁移工具 | 自写显式 migration（版本表 + 顺序脚本），不引入 ORM |
| 日志 | `pino`（结构化 JSON，便于脱敏与关联 request_id） |
| Schema 校验 | Zod（版本以 `packages/contract` 锁定为准） |
| Codex TOML | `smol-toml@1.9.1`，只解析 allowlist 非秘密字段 |
| monorepo 消费 | `packages/contract` 通过 TS project references 源码直引，不做构建产物 |

实现顺序约束：

- Credentials 先实现 `FakeCredentialStore` 和 `CredentialStorePort` Contract Test，再接入各平台 Keychain；具体库不进入 Domain 或 Application；
- Codex 配置导入只解析允许字段，TOML 解析器不得把原始文件或秘密写入 DTO、日志、SQLite 或 Store；
- SQLite 先落 migration、索引和事务测试，再接入 Application；
- HTTP 安全 Header、Origin/Host、速率限制、CSRF 和脱敏策略集中在 `http-ws` 配置，不散落在 Controller。

## 6. UI 设计方向

参考 AionUI，但**只移植架构与交互模式，不移植组件实现**。

**照搬**：

- 语义化 CSS 变量 token 分层（背景阶 `--bg-1..10`、文字 `--text-primary/secondary/disabled`、边框、语义状态色），明暗两套值；
- 布局尺寸常量（侧边栏 260 / 最小 200 / 收起 0、标题栏 36px）；
- 交互模式：消息气泡几何（用户右对齐、AI 左对齐全宽）、工具调用行 + 状态徽标、权限请求内联卡片单击提交、Agent 状态点、会话时间线分组；
- Markdown 排版阶梯与等宽字体栈；
- 以边框而非阴影做分隔的整体克制风格。

**不照搬**：

- Arco Design 组件与其 `--color-*` / `--primary-6` 色阶（改用 Naive UI 与 `n-*` token）；
- `@icon-park/react`（React 组件库，改用 `@iconify/vue` 或 `unplugin-icons`）；
- Shadow DOM Markdown 渲染（React 实现，Vue 需重写）；
- Electron 专有部分（标题栏拖拽区、窗口控制、IPC 主题广播）。

**要有自己的取舍**：AionUI 的色值作为起点，但不要做成同一套视觉，避免两个产品看起来一样。

样式与主题的两个硬约束（UnoCSS preflight 与 Naive UI 冲突、暗色模式统一开关）见 [Web UI 模块](../modules/web.md)。
