# 接入层能力矩阵

> 本文记录 ACP Adapter 的**实测结果**，不是推测。数据来源见「实测方法」。
> 唯一目的：让 Rolecast 只依赖已验证的能力，不按 CLI 行为或文档宣传推断。

## 1. 实测方法

- 环境：macOS，Node v22.21.1
- 被测版本：`@agentclientprotocol/claude-agent-acp@0.90.0`、`@agentclientprotocol/codex-acp@2.2.2`
- 方法：自写最小 ACP 客户端，spawn Adapter 子进程，走 `initialize` → `session/new` → `session/set_config_option` → `session/prompt`，记录全部收发报文
- 客户端声明能力：`fs: { readTextFile, writeTextFile }`、`terminal: true`

实测日期：2026-10-14。Adapter 版本变化后必须重测。

## 2. 握手能力对比

`initialize` 返回的 `agentCapabilities`：

| 能力 | Claude | Codex |
| --- | --- | --- |
| `protocolVersion` | 1 | 1 |
| `authMethods` | **空数组** | `api-key`、`chat-gpt` |
| `mcpCapabilities` | `http: true`、`sse: true` | `http: true`（`acp`/`sse` 为 false） |
| `sessionCapabilities` | additionalDirectories、close、delete、fork、list、resume | 同上 **+ subagents** |
| `promptCapabilities` | image、embeddedContext | image、embeddedContext |
| `loadSession` | true | true |
| 额外 `_meta` | `claudeCode.promptQueueing`、`steering.supported` | `steering.supported` |

### 2.1 认证差异（重要）

- **Codex 在默认客户端能力下暴露两种 ACP 认证方法**：`api-key`、`chat-gpt`。这只说明 Adapter 声明了哪些方法；Rolecast 的认证执行、成功状态、回调归属和凭据交接**均未验证**（见 Phase 1C）。
- **Claude 不暴露任何 ACP 认证方式**（`authMethods: []`），且 `_auth/status_update` 报 `{"kind":"none","label":"Not logged in"}`。
- 但 Claude **仍然能正常执行**——实测中模型调用、工具调用全部成功。原因是它读取环境变量（`ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_BASE_URL`）与本地配置。

**结论**：Claude 的认证不走 ACP，只能依赖运行环境已具备的凭据。Rolecast 无法为 Claude 提供 UI 内登录流程。

> 补充（Phase 1C 复核，`claude-agent-acp@0.90.0` / `codex-acp@2.2.2`）：上面的「Claude 不暴露认证方式」只在**默认客户端能力**下成立。声明 `terminal: true` + `auth.terminal: true` 后，Claude 会给出 `claude-ai-login` / `console-login`（`type=terminal`，需客户端另起交互终端，不能传给 `authenticate`）；声明 `auth._meta.gateway: true` 后给出 `gateway` / `gateway-bedrock`。Codex 声明 `elicitation: { url: {} }`（**对象**，顶层）后增加 `chat-gpt-device-code`，声明 gateway 元能力后增加 `gateway`。Codex 的 auth method **不带 `type` 字段**，只能按 method ID 分类。上述能力只说明「可声明什么」，不代表认证成功或凭据交接已验证。

## 3. 会话配置项（configOptions）

`session/new` 返回 `configOptions`，每项含 `id`、`category`、`type`、`currentValue`、`options[]`。

| category | Claude | Codex |
| --- | --- | --- |
| `mode` | 5 项 | 4 项 |
| `model` | 6 项 | 8 项 |
| `thought_level` | `effort`，6 项 | `reasoning_effort`，6 项 |
| 其他 | `agent`（主线程 persona） | `collaboration_mode`、`fast-mode` |

### 3.1 权限模式

```text
Claude: default / acceptEdits / plan / auto / bypassPermissions
Codex:  read-only / workspace-write / agent / agent-full-access
```

两套语义**不对应**，Rolecast 不能做统一映射表硬编码，只能透传各自的可选值。

### 3.2 模型与思考等级

- **Claude**：`model` 与 `effort` 是两个独立维度。`model` 选项来自用户环境（实测中为 `default`/`opus`/`fable`/`sonnet`/`haiku` + 一个自定义模型），说明 Adapter 读取了用户的模型覆盖环境变量。
- **Codex**：`model`（8 个家族）与 `reasoning_effort` 是两个独立维度；但 `models.availableModels` 又提供 44 个把 effort 编码进 modelId 的组合（如 `gpt-6.1-sol[low]`）。**两套表示并存**。

**Rolecast 的选择**：统一用 `configOptions` 的 `model` + `reasoning_effort` 两个独立维度（ACP 标准结构，与 Claude 的 `model` + `effort` 对齐）。`availableModels` 只用于取展示名称与描述，不作为可选项来源。这样两个 Provider 在 RoleBinding 里是同一套结构，不需要为 Codex 单独建映射。

### 3.3 切换已验证

`session/set_config_option` 对 Claude 与 Codex 的 `model`、`effort` / `reasoning_effort`、`mode` 均调用成功，返回更新后的完整 `configOptions`。

**这是 RoleBinding 可以落到 ACP 的直接依据。**

## 4. 执行与工具调用

`session/prompt` 实测可正常执行，工具调用以 `session/update` 事件流下发。

Claude 实测工具事件：

```text
kind=edit    title="Preparing file…"   status=pending → completed
kind=edit    title="Write /path/probe-ok.txt"
```

Codex 实测工具事件：

```text
kind=execute title="printf '%s' 'hello' > probe-ok.txt"   status=in_progress → completed
```

`session/prompt` 结果返回 `stopReason` 与 `usage`，**含按模型拆分的 `model_usage`**（实测中 Claude 一轮内出现两个模型条目：主模型与快速模型）。可用作成本统计来源。

## 5. 权限请求报文形态

Codex 在 `read-only` 模式下写文件时，触发 `session/request_permission`：

```json
{
  "sessionId": "...",
  "toolCall": {
    "toolCallId": "exec-...",
    "title": "Run command",
    "rawInput": { "command": "printf '%s' 'hello' > probe-ok.txt", "cwd": "..." },
    "kind": "execute",
    "status": "pending"
  },
  "options": [
    { "optionId": "allow_once", "name": "Yes, proceed", "kind": "allow_once" },
    { "optionId": "accept_execpolicy_amendment", "name": "Yes, and don't ask again ...", "kind": "allow_always" },
    { "optionId": "cancel", "name": "No, and tell Codex what to do differently", "kind": "reject_once" }
  ]
}
```

应答格式（实测有效）：

```json
{ "outcome": { "outcome": "selected", "optionId": "allow_once" } }
```

要点：

- 选项 `kind` 有 `allow_once` / `allow_always` / `reject_once` 三类；
- `options` 由 Adapter 决定，Rolecast 只能渲染与回传，不能自行增删；
- **不应答会挂起**，与既有风险判断一致；
- 权限模式影响是否触发：`read-only` 下写文件必触发；`agent`（Codex 默认）下普通写文件不触发。

## 6. 实测发现的坑

### 6.1 用户环境会污染会话

`available_commands_update` 下发了用户全局安装的命令与技能，且被标注为 `(user)`。实测中 Claude 侧 62–66 个、Codex 侧 60 个，包含 `ccb-clear`、`computer-use`、`file-op` 等与本项目无关的条目。

**影响**：Agent 行为会被用户个人环境改变，Rolecast 无法保证同一 Role 在不同机器上行为一致。

### 6.2 Claude 的模型列表来自环境

Claude 的 `model` 选项实测为 `default` / `opus` / `fable` / `sonnet` / `haiku` + 一个自定义模型，对应的是用户环境里的模型覆盖变量，不是 Anthropic 官方模型名。

**影响**：不能把模型列表当稳定契约；必须每次从握手读取并标注来源。

### 6.3 两个 Adapter 的会话能力不对等

Codex 有 `sessionCapabilities.subagents`，Claude 没有。Codex 的 `mcpCapabilities` 不含 `acp`，Claude 支持 `sse`。

**影响**：不得假设两者能力对等，也不得在 Orchestration 里按 Provider 分支。

### 6.4 `authMethods` 为空不等于不可用

Claude 报「Not logged in」且无认证方式，但实测执行完全正常。

**影响**：不能用 `authMethods` 判断「是否可用」；必须实际连接测试。

## 7. 参照实现：AionCore 的路由选择

AionCore（AionUI 的 Rust 后端）在同一对 Provider 上做出了与 Rolecast 不同的选择，值得记录。

### 7.1 它把 Provider 分成两类

`crates/aionui-ai-agent/src/factory/acp.rs:31-39`：

```rust
enum BackendRoute {
    /// claude/codex — direct-CLI via `build_session_instance`.
    DirectCli,
    /// agy — direct-CLI via its own factory (does NOT speak ACP).
    Antigravity,
    /// A real ACP vendor: the `AcpAgentManager` handshake path.
    AcpManager,
}
```

```text
claude / codex / agy   →  direct-CLI（自拼 CLI 参数，自实现协议）
其余 18+ 个 vendor     →  ACP
```

同文件 106-111 行注释：

> claude/codex **ALWAYS** run through the clean-slate direct-CLI SessionBackend, **NOT** the ACP manager. There is no fallback: a claude/codex build that yields no instance is a hard error, not a silent drop to ACP.

### 7.2 这是一次有意的迁移

CHANGELOG 与提交 `14efff8`（PR #609）记录了迁移。提交信息原文：

> routes **claude** and **codex** through it via `SessionAgentTask`, **talking to each CLI over its native wire instead of a third-party ACP shim**.
> opencode/gemini/hermes remain on the `AgentInstance::Acp` path (unchanged).

它明确把 ACP Adapter 称作「third-party ACP shim」。

### 7.3 迁移换来的能力

提交信息列出的收益，即 ACP 路径当时给不了的：

- **claude** 走 `--print stream-json` 控制协议：spawn 时传 `--permission-mode`、in-band `set_permission_mode` / `set_model`、用 control-request 拿模型与斜杠命令目录；
- **codex** 走 app-server JSON-RPC：`thread/start`、`thread/settings/update`、`permissionProfiles/list`、反向 RPC 审批；
- **per-model reasoning effort 作为配置项**，含 **`ultracode`** 这个额外的 effort 档位（仅 xhigh 能力的模型）；
- 审批可在 reload 后通过 pending-approval 注册表恢复；
- 更细的诊断：被拒的 mode/model/effort 切换、codex 越界警告、空轮次提示、进程无 EOF 退出与断连被归为终态。

### 7.4 一个反直觉细节

AionCore 运行时目录里**装了** `claude-agent-acp` 与 `codex-acp`，但报错信息显示它找的是包内捆绑的 CLI 二进制：

```text
runtime\acp\claude-agent-acp\0.58.1\...\@anthropic-ai\claude-agent-sdk-win32-x64\claude.exe
runtime\acp\codex-acp\1.1.2\...\@openai\codex-win32-x64\vendor\...\codex.exe
```

即 **ACP Adapter 包被当作 CLI 二进制的分发渠道**，而不是协议适配器。这与本文 §1 实测到的「Claude 路径实际运行 SDK 内嵌运行时」一致。

### 7.5 环境隔离：确认未做

| 检查项 | 结果 |
| --- | --- |
| 自定义 HOME / USERPROFILE | 未设置，继承后端真实 HOME |
| `CLAUDE_CONFIG_DIR` / `CLAUDE_PROJECTS_ROOT` / `CLAUDE_CODE_*` | 未设置，claude 读用户全局 `~/.claude` |
| `CODEX_HOME` / `CODEX_SESSION_ROOT` | 未设置，codex 用 `~/.codex` |
| `--settings` / `settingSources` | 全仓库不存在 |
| cwd | workspace（非 tmpdir） |
| env 继承 | ACP 通道 `env_clear()` 后又灌回「父进程 env ∪ 登录 shell env」；direct-CLI 通道无 `env_clear()`，全量继承 |

唯一接近隔离的是托管 Node 运行时的 npm 配置（`npm_config_cache` / `npmrc` 指向受控目录），不涉及 HOME。

**结论**：AionCore 不隔离 `~/.claude` / `~/.codex`，所有会话、项目、agent 共享同一份用户全局状态。本文 §6.1 记录的「用户环境污染会话」是有意的产品选择，不是缺陷。

### 7.6 对 Rolecast 的判断

- AionCore 的选择说明 **ACP 是够用但不是唯一**；它换来的是更深的控制与诊断。
- 它付出的代价是自实现两套 CLI 原生协议（整个 `aionui-session` crate）。
- **Rolecast 当前不需要这些**：本文 §3.3 已实测 ACP 支持按 Session 选模型与 effort，§5 已验证权限请求中转可用。Rolecast 需要的是角色绑定、权限中转、事件流与持久化，ACP 均已覆盖。
- 因此 ADR-003 维持「ACP 优先」，但**必须记录逃生口**：若后续发现 ACP 无法满足某项必需能力，Claude/Codex 可改为直连 CLI 原生协议，参照实现为 AionCore 的 `aionui-session` crate（`claude_conn` / `codex_conn`）。

## 8. 环境隔离实测

上一版把「能否隔离」列为待验证。已实测，结论：**两个 Provider 都尊重各自的配置目录变量，但代价差很多。**

### 8.1 Claude — `CLAUDE_CONFIG_DIR` 生效

| 观察项 | 基线（不隔离） | 隔离后 |
| --- | --- | --- |
| 隔离目录内容 | — | 被完整写入：`.claude.json`、`backups/`、`projects/`、`sessions/` |
| 全局 `~/.claude` mtime | — | **未变** |
| 可用命令数 | 66 | 47 |
| 模型选项 | 6 项 | 6 项（**不变**） |

消失的 19 个命令全部是用户个人安装的：

```text
all-plan  ask  autonew  ccb-clear  computer-use  continue  file-op
find-skills  frontend-design  i-have-adhd  karpathy-guidelines  pend
ping  ponytail  review  sync-local  tp  tr  web-design-guidelines
```

保留的 47 个是 Claude Code 内置命令（`compact`、`config`、`doctor`、`code-review`、`effort` 等）。

**隔离粒度正好**：去掉用户个人污染，保留工具自身能力。且因为凭据走环境变量（`ANTHROPIC_AUTH_TOKEN` 等），隔离后**仍能正常执行**。

### 8.2 Codex — `CODEX_HOME` 完全生效

| 观察项 | 基线 | 隔离后 |
| --- | --- | --- |
| 可用命令数 | 60 | **0** |
| 认证状态 | `gateway` / "Custom model gateway" | `none` / "Not logged in" |
| 模型列表 | 8 个家族 | **null**（读不到网关配置） |
| 全局 `~/.codex` mtime | — | **完全未变**（前后同一时刻） |
| 隔离目录内容 | — | sqlite 状态、`installation_id`、`skills/`、`tmp/` |

Phase 0 使用锁定 Adapter 重新验证时，若 `CODEX_HOME` 指向全新空目录，Codex 可能在 `session/new` 返回 `Authentication required`，而不是返回可用模型列表。这是预期的 `needs_configuration` 结果，不得静默回退到 inherited；完成已确认的非秘密配置导入并绑定 API key 的 `credential_ref` 后，才允许继续测试会话。

### 8.3 关键差异

- **Claude 隔离几乎零成本**：凭据与模型来自环境变量，config dir 只承载会话状态与个人技能；
- **Codex 隔离后开箱不可用**：用户的自定义网关、模型目录、登录态全在 `~/.codex` 内，隔离等于要求用户从零配置；
- 因此隔离开关**不能对两个 Provider 一视同仁**：Claude 侧可直接启用；Codex 侧必须配套「配置导入」或首次引导，否则应用不可用。

### 8.4 已确定的实现边界

- Rolecast 默认使用 `environment_mode=inherited`，以兼容用户已有环境；
- `environment_mode=isolated` 时，运行时目录只由 Rolecast 派生，不能软链接 `~/.claude` 或 `~/.codex`；
- Claude 可直接注入现有环境凭据并设置 `CLAUDE_CONFIG_DIR`；
- Codex isolated 必须先完成 preview → 用户确认 → apply 的非秘密配置导入，不能复制 `auth.json` 或整份 `~/.codex`；API Key 通过 `credential_ref` 注入；登录流程不在产品范围，isolated 不接受继承的登录态；
- ACP Runtime 只能使用已确认的 ProviderConnection 字段翻译 Adapter 配置，不得自行读取全局配置并覆盖 Rolecast 配置；
- 如果当前 Adapter 版本没有可验证的显式配置入口，Codex isolated 状态必须显示「需要配置」，不得静默回退到 inherited。

## 9. 对 Rolecast 的直接约束

1. **模型与思考等级从握手读取，不硬编码**——两个 Adapter 的可选值不同且随环境变化；
2. **权限模式只透传，不做跨 Provider 映射**；
3. **Claude 默认不暴露 ACP 认证方法**，只能读取环境凭据；Codex 声明了可调用的认证方法，但 Rolecast 不接入认证执行。产品认证只支持 inherited 本地 CLI 或 isolated API key，不实现登录流程；
4. **权限请求必须中转**，且只渲染 Adapter 给出的选项；等待请求默认 5 分钟软提醒、30 分钟硬超时，过期后不能再次回答；
5. **成本统计可用 `usage.model_usage`**，按模型拆分；
6. **Adapter 版本必须锁死并记录**，升级后重跑本文实测；
7. **配置来源必须唯一且可审计**：inherited 明确继承全局环境，isolated 明确使用 ProviderConnection，不允许隐式混用。

### 9.1 版本升级后的必测项

Adapter 升级后除原有握手、配置、权限和流式事件检查外，必须增加：

- `CLAUDE_CONFIG_DIR` / `CODEX_HOME` 是否仍隔离全局目录；
- Codex 非秘密配置入口是否仍能从 ProviderConnection 生效；
- 权限请求拒绝/取消应答与过期后的错误是否保持兼容。

这类变化必须先更新本矩阵，再修改实现。
